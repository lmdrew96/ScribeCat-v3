# Codebase Review: ScribeCat v3
**Date:** 2026-08-25
**Stack:** React 19, TypeScript, Vite 7, Convex, Clerk, TanStack Router, TipTap, Tailwind 4 + shadcn/ui, Excalibur.js
**Project type:** Web app (PWA), v5.20.1

## Executive Summary

ScribeCat has grown enormously since the last documented milestone (docs/PHASES.md stops at v4.27.0; the app is now at v5.20.1 — roughly 90 versions of undocumented feature work, including an entire RPG game). The core recording → notes → study loop is solid and consistently styled, and recent work (session search/sort, R2 migration, MCP server) shows good engineering discipline. The two biggest opportunities: (1) the flagship "Generate Notes" action still ships debug `console.log` calls and native `alert()` popups that break the app's toast/glassmorphism conventions everywhere else, and (2) the app has no onboarding for a genuinely large feature surface (recording, 6 study tools, friends, DMs, rooms, exam rooms, and a full dungeon-crawler RPG), which risks losing new users in the nav.

## High Priority Findings

### 1. `alert()` and leftover debug logging in the core "Generate Notes" flow
- **What**: `notes-panel.tsx:211-297` (`handleGenerateNotes`) — the button that drives the app's primary AI feature — uses `alert()` for all four of its error paths and has 8 `console.log`/`console.error` debug statements left in, including full JSON dumps of editor content. Every other AI/async action in the app (31 other files) uses `sonner` toasts instead.
- **Why it matters**: `alert()` is a blocking native dialog that clashes with the glassmorphism UI, can't be styled, and reads as unfinished/buggy next to the rest of the app. The console spam also leaks transcript/notes content into devtools in production.
- **Suggested action**: Replace the four `alert()` calls with `toast.error(...)` (already imported elsewhere via `sonner`), and delete the `console.log` debug lines.
- **Effort estimate**: Quick fix (~20 min).

### 2. No onboarding for a very large feature surface
- **What**: New users land straight in `HomeView` after sign-in with zero guided intro. The app now spans recording, notes, 6 AI study tools, StudyQuest (a ~6,500-line RPG with dungeon exploration, turn-based combat, shop, inventory), friends, DMs, study rooms with multiplayer games, and exam rooms — none of it has a first-run tour, tooltip walkthrough, or empty-state guidance pointing a new user to what to try first.
- **Why it matters**: This is exactly the kind of cognitive-load cliff that hurts ND users most — a wall of nav items and no anchor for "what do I do first." Given the target audience (ADHD students), an unguided drop into 6+ top-level surfaces plus a whole second app-within-the-app (StudyQuest) is a real onboarding gap.
- **Suggested action**: A lightweight first-run checklist or spotlight ("Record your first lecture" → "Try Generate Notes" → "Meet your study cat") would go a long way. Doesn't need to be elaborate — even a dismissible welcome card on `HomeView` for first-time users.
- **Effort estimate**: Half-day for a minimal version.

### 3. StudyQuest game has no touch/mobile input
- **What**: The Excalibur.js-powered game (`components/study-quest/game/`) is keyboard-only — movement is WASD/arrows (`game/scenes/town.ts:9`), combat is mouse/keyboard driven, and there's no `touchstart`/`pointerdown` handling anywhere in the game code. Meanwhile the rest of the app has real mobile investment: a dedicated `useIsMobile` hook used in 25+ places, a mobile nav drawer, and (per git history) iPad/Apple Pencil support.
- **Why it matters**: Students are a mobile/tablet-heavy audience, and this is now the single largest feature by line count in the app (~6,500 lines across `study-quest/`). If it's unusable on touch devices, a large fraction of users can adopt the recording/notes/study-tools side of the app but never open the game they're being rewarded with XP for.
- **Suggested action**: At minimum, gate the "Explore Town" / battle screens behind a "desktop only for now" notice on mobile rather than presenting a broken control scheme; ideally add an on-screen d-pad + tap-to-attack for touch.
- **Effort estimate**: Multi-day for real touch controls; quick fix for a mobile notice/gate in the meantime.

### 4. Documentation is ~90 versions stale
- **What**: `docs/PHASES.md`'s version history table ends at v4.27.0 (Apr 2026). Everything since — StudyQuest's entire existence (game, shop, inventory, battle system, evolution tiers), the MCP server, R2 storage migration, session merging, speaker detection, handwriting notes, flagged words, failsafe recording — is undocumented there. The root `CLAUDE.md` also still describes "Current Version: 4.29.0" and doesn't mention StudyQuest's game layer, the MCP server, or R2 at all.
- **Why it matters**: This is the reference future-you (or Cody) uses to orient on the project. Right now it undersells the app by an entire game and a public API surface (MCP), and a new contributor reading it would have no idea `convex/mcpApi.ts`, `shop.ts`, `inventory.ts`, or the `study-quest/game/` engine exist.
- **Suggested action**: Batch-update `docs/PHASES.md`'s version table and `CLAUDE.md`'s "Current Version"/structure sections to reflect v5.20.1. Worth doing as its own pass rather than folding into feature work.
- **Effort estimate**: Half-day.

## Medium Priority Findings

### 5. Four files exceed the project's own 500-line file limit
- **What**: `settings-modal.tsx` (1,164 lines), `nugget-chat.tsx` (664), `editor-toolbar.tsx` (652), `study-content.tsx` (628) on the frontend; `studyGames.ts` (772), `examRooms.ts` (629), `sessions.ts` (592), `studyRooms.ts` (529) in Convex. `CLAUDE.md` states "Max 500 lines per file, single responsibility."
- **Why it matters**: `settings-modal.tsx` at 1,164 lines is over double the limit and mixes theme selection, sound settings, notification prefs, goals, and account info in one file — the kind of file where a small change risks an unrelated regression elsewhere in the same component.
- **Suggested action**: Split `settings-modal.tsx` into per-tab components (`settings/theme-tab.tsx`, `settings/notifications-tab.tsx`, etc.) driven by the existing tab structure. Lower priority for the others unless they're being actively touched.
- **Effort estimate**: Half-day for settings-modal; skip the rest unless you're in there anyway.

### 6. Zero automated tests
- **What**: No `*.test.*`/`*.spec.*` files anywhere in the repo, no test runner configured.
- **Why it matters**: For a project at this scale (31 schema tables, real-time multiplayer games, AI pipelines, payment-free but XP/economy logic in StudyQuest), regressions currently rely entirely on manual testing before each commit. The XP/leveling math (`xpUtils.ts`) and the shop/inventory economy in particular are exactly the kind of pure-logic code that's cheap to unit test and easy to silently break.
- **Suggested action**: Not asking for full coverage — start with `xpUtils.ts` and `weakSpots.ts` (pure functions, high value, no Convex/React setup needed) using Vitest.
- **Effort estimate**: Half-day to set up Vitest + first test file; ongoing after that.

### 7. MCP server is read-only
- **What**: `convex/mcpApi.ts` exposes `mcpListSessions`, `mcpGetSession`, `mcpSearchSessions`, `mcpGetCourses` — all reads. There's no way for an MCP client (e.g., Cody, another Chaos app) to create a session note, append to nugget notes, or trigger note generation.
- **Why it matters**: This is a nice-to-have, not a gap — the read-only surface is a reasonable v1. But it means ScribeCat can be *read* by the Chaos ecosystem but not *written to* — e.g. Cha(t)os or Personal Context couldn't push a quick note into a session on the user's behalf.
- **Suggested action**: If there's a concrete use case (e.g. "let Cody add a note to today's lecture from chat"), add a scoped `mcpAppendNote` write endpoint later. Not urgent.
- **Effort estimate**: Half-day, only if/when a use case shows up.

### 8. Landing page and theme-swatch colors are hardcoded hex, not theme tokens
- **What**: `landing-page.tsx` has ~15 raw hex values in Tailwind arbitrary-value classes (`from-[#8cbdb9]/20`, `border-[#dea549]/30`, etc.) for card gradient accents.
- **Why it matters**: Minor — the landing page is pre-auth/pre-theme by nature, so this may be intentional. But if the ADHDesigns palette ever shifts (as it did recently per your memory notes), these won't pick it up automatically the way `bg-adhd-*` classes would.
- **Suggested action**: Low urgency; consider swapping to `--adhd-*` tokens next time the landing page gets touched.
- **Effort estimate**: Quick fix, whenever convenient.

## Low Priority / Nice-to-Have

- **StudyQuest not in top nav**: `/study-quest` exists as a route but isn't listed in `top-bar.tsx`'s `navItems` — it's only reachable via the floating widget. This may be intentional (keeps the game feeling ambient rather than like a chore), but worth a deliberate check that it's discoverable enough given how much of the app it now represents.
- **`handwriting-canvas.tsx` uses raw canvas fillStyle hex** (`#ffffff`/`#000000`) rather than theme vars — fine since Canvas 2D context can't consume CSS custom properties directly without `getComputedStyle`, just flagging for awareness if dark-mode drawing ever becomes a request.

## Dimension Summaries

### UI/UX: 🟡 Adequate — mostly consistent, one jarring inconsistency
Strong patterns overall: consistent glassmorphism, mobile drawer nav with badge counts, `sr-only` labels on icon buttons in `top-bar.tsx`, shadcn components carry proper `focus-visible` rings by default. The `alert()`/console-log issue in notes-panel (#1) is the one place that visibly breaks the pattern. No onboarding (#2) is the other real gap.

### Features: 🟢 Solid — deep and mostly complete, one accessibility hole
Feature-complete relative to its own ambitions and then some — the StudyQuest RPG is a genuinely large addition beyond the documented Phase 4 scope. Recent session search/sort/course-grouping (v5.19.0) and session merge (v5.17.0) show the team is actively closing quality-of-life gaps. Main hole is mobile input support for the game (#3).

### MCP: 🟢 Solid — clean read API, room to grow
`mcpApi.ts` is well-structured (SHA-256 hashed API keys, scoped internal queries, sensible response shaping). Read-only is a fine v1 scope (#7).

### Architecture: 🟡 Adequate — a few oversized files
Convex module boundaries are clean (one concern per file, consistent query/mutation/httpAction patterns). The main issue is a handful of files that outgrew the project's own 500-line convention (#5), `settings-modal.tsx` most notably.

### Infrastructure: 🟢 Solid
CSP is actively maintained (recent R2 CSP fix in git history), PWA is configured, R2 migration for file storage is complete. No red flags found in `vite.config.ts` or build scripts.

### DX: 🟡 Adequate — docs badly lag actual state
Biome + Husky + lint-staged pre-commit hooks are solid. The two gaps are stale docs (#4) and zero test coverage (#6) — both fixable without touching product code.

## Strengths

- **Consistent toast/error pattern almost everywhere** — 31 files correctly use `sonner`, `notes-panel.tsx` is the outlier, not the norm.
- **Real mobile investment**: `useIsMobile`, a proper drawer nav, tab-based mobile layouts in `HomeView`, and iPad/Apple Pencil support show mobile isn't an afterthought — which makes the StudyQuest gap more visible in contrast, not less.
- **Fast iteration on real user-facing bugs**: git history shows a tight loop of ship → find real playback/CSP/race-condition bug → fix within a version or two (e.g. the WebM duration, CORS, and CSP fixes around v4.6.x, and the recent R2 CSP fix).
- **StudyQuest is a genuinely creative gamification layer** — XP tied to real study behavior (recording time, tool use, daily goals) rather than bolted-on points is a good ND-design instinct: it rewards the actual desired behavior.
